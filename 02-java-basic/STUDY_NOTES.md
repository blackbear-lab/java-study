### クラスが必要な理由

- 名前、年齢、成績を別々の配列にすると、同じ添字で関連を維持する必要がある
- 一つの配列だけを変更すると、対応関係が崩れる可能性がある
- クラスを使用すると、関連するデータを一つの型として表現できる

```java
class Student {
    String name;
    int age;
    int grade;
}
```

### オブジェクトの生成と使用

```java
Student student = new Student();
student.name = "田中";
student.age = 20;
student.grade = 90;
System.out.println(student.name + ": " + student.grade);
```

| 用語 | 意味 |
| --- | --- |
| クラス | データと振る舞いを定義する型 |
| オブジェクト | 実行時に生成される実体 |
| インスタンス | あるクラスから生成された実体を、そのクラスとの関係で表す言葉 |
| 参照 | オブジェクトにアクセスするための値 |

- `new Student()`はインスタンスを生成し、その参照を返す
- 変数そのものにオブジェクト全体が格納されるわけではない
- 参照は実装に依存するため、Javaから直接扱える物理メモリアドレスと同一視しない

### 配列による管理

```java
Student first = new Student();
first.name = "田中";
first.grade = 90;
Student second = new Student();
second.name = "佐藤";
second.grade = 85;
Student[] students = {first, second};
for (Student student : students) {
    System.out.println(student.name + ": " + student.grade);
}
```

- 配列には各オブジェクトへの参照が格納される
- `new Student[2]`だけでは、二つの`Student`は生成されず、各要素は`null`になる
- 配列とループを使用すると、人数ごとに同じ表示処理を書く必要がなくなる

- 商品名・価格・数量を持つクラスを作成する
- 商品の配列を走査し、`価格 × 数量`の合計金額を計算する
- データの追加時に表示処理を増やさずに済むことを確認する

### 代入時にコピーされるもの

| 分類 | 例 | コピーされる値 |
| --- | --- | --- |
| 基本型 | `int`、`boolean`、`double` | 数値や真偽値など |
| 参照型 | クラス型、配列型、インターフェース型 | オブジェクトなどへの参照、またはnull |

```java
int a = 10;
int b = a;
b = 20;
System.out.println(a); // 10

Student first = new Student();
first.grade = 90;
Student second = first;
second.grade = 100;
System.out.println(first.grade); // 100
```

- 基本型でも参照型でも、代入では変数が持つ値をコピーする
- 参照をコピーしても、別のオブジェクトが自動的に生成されるわけではない

### メソッド呼び出しは値渡し

```java
static void change(Student target) {
    target.grade = 100;
}

static void replace(Student target) {
    target = new Student();
    target.grade = 50;
}
```

- `change(student)`は、コピーした参照から同じオブジェクトを変更する
- `replace(student)`は、引数変数の参照だけを変更するため、呼び出し元の変数は置き換わらない
- Javaは参照型の場合も値渡しであり、「呼び出し元の変数そのもの」を渡すわけではない
- 新しいオブジェクトを返して置き換える場合は、`student = createStudent();`のように戻り値を代入する

### 初期化とnull

| 対象 | 初期化の扱い |
| --- | --- |
| 数値のフィールド・配列要素 | 0に相当する値 |
| booleanのフィールド・配列要素 | false |
| 参照型のフィールド・配列要素 | null |
| ローカル変数 | 使用前に明示的な代入が必要 |

- `null`は、オブジェクトを参照していないことを表す
- `null`に対するインスタンスメソッド呼び出しやフィールドアクセスは、`NullPointerException`の原因になる
- `null`のラッパー型を基本型に自動変換する場合も例外になる
- 例外が発生した行を確認し、その式のどの参照が`null`なのか調べる
- 必須データを初期化する設計と、必要な箇所での`null`チェックを使い分ける

- メソッド内のフィールド変更と引数への再代入を比較する

### データと振る舞いをまとめる

1. バラバラの変数と処理で動作を表現する
2. 関連するデータをクラスにまとめる
3. 重複する処理をメソッドに抽出する
4. データを扱う処理を、そのデータを持つクラスに移す

```java
class MusicPlayer {
    private int volume;
    private boolean on;

    void turnOn() { on = true; }
    void turnOff() { on = false; }
    void volumeUp() { volume++; }
    void showStatus() {
        System.out.println("電源: " + on + ", 音量: " + volume);
    }
}
```

- 状態はフィールド、振る舞いはメソッドとして表現する
- 呼び出し側は`turnOn()`などの操作を利用し、内部の状態変更をクラスに任せられる

- オブジェクト指向でも、メソッド内部には手続き的な処理を記述する

| 観点 | 処理を外部に置く構成 | オブジェクトに操作をまとめる構成 |
| --- | --- | --- |
| 状態の変更 | 呼び出し側が直接操作しやすい | 対象のメソッドを通して操作 |
| 変更の影響 | 内部データを知るコードに広がりやすい | 操作の契約を維持すれば抑えやすい |
| 設計時の着眼点 | 処理の順序 | 責務とオブジェクト間の協調 |

### 初期化を生成時に行う

```java
class Member {
    String name;
    int age;

    Member(String name) {
        this(name, 0);
    }

    Member(String name, int age) {
        this.name = name;
        this.age = age;
    }
}
```

- コンストラクタ名はクラス名と同じで、戻り値の型を記述しない
- `void Member()`は通常のメソッドであり、コンストラクタではない
- `this.name`は現在のインスタンスのフィールド、`name`は引数を表す
- `this(...)`は同じクラスの別のコンストラクタを呼び出す
- この例では`this(...)`を先頭に置く基本形で、初期化処理を共通化している
- コンストラクタ呼び出しが循環する定義はできない

### デフォルトコンストラクタの注意点

- コンストラクタを一つも宣言しない場合、コンパイラがデフォルトコンストラクタを追加する
- 引数付きコンストラクタを宣言すると、引数なしコンストラクタは自動追加されない
- 引数なしで生成したい場合は、必要に応じて明示的に定義する
- コンストラクタに必須値を渡す設計にすると、初期化の呼び忘れを防ぎやすい
- 不正値を拒否するには、引数を受け取るだけでなく検証処理も必要になる

- 価格を省略した場合は0になるよう、オーバーロードと`this()`を使用する

### クラスの分類と利用

```java
// ファイル: study/member/Member.java
package study.member;

public class Member {
}
```

```java
// ファイル: study/app/Main.java
package study.app;

import study.member.Member;

public class Main {
    public static void main(String[] args) {
        Member member = new Member();
    }
}
```

- 完全修飾名は`study.member.Member`のようにパッケージ名とクラス名を含む
- `import`は型名の記述を簡潔にするためのもので、アクセス制限を解除する機能ではない
- 同じパッケージの型と`java.lang`の型は、通常、明示的な`import`なしで利用できる
- `import study.member.*;`は、その配下のサブパッケージの型まで取り込まない
- 同名のクラスを同時に使う場合は、片方または両方を完全修飾名で記述する
- パッケージ名は小文字を基本とし、組織の逆ドメイン名などを利用する
- `study`と`study.member`は別のパッケージであり、親子の名前だけで特別なアクセス権は得られない

**復習用演習**

- 注文、商品、会員を別パッケージに分け、必要なクラスを`import`する

| 修飾子 | 基本的なアクセス範囲 |
| --- | --- |
| `private` | 宣言したクラスの内部を基本とする |
| 指定なし | 同じパッケージ |
| `protected` | 同じパッケージ、および別パッケージのサブクラスからの所定のアクセス |
| `public` | 他のパッケージからも利用可能 |

- 指定なしのアクセスはパッケージアクセスと呼び、`default`という修飾子を書くわけではない
- 通常のトップレベルクラスでは`public`または指定なしを使用する
- `private`と`protected`は通常のトップレベルクラスには指定できない
- 別パッケージのサブクラスからの`protected`アクセスには、参照する式の型などにも制約がある
- ネストしたクラスやモジュールには追加の規則があるため、上表は基本的な範囲として理解する

### カプセル化の例

```java
class BankAccount {
    private int balance;

    public void deposit(int amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("正の金額を指定する");
        }
        balance += amount;
    }

    public int getBalance() {
        return balance;
    }
}
```

- フィールドを非公開にし、状態変更の規則をメソッドに集約する
- 無条件のsetterをすべて公開すると、不正な値を防ぐ目的を達成できない場合がある
- 外部から必要な操作だけを公開し、内部実装への依存を減らす
- getterで可変オブジェクトそのものを返すと、内部状態を変更される場合がある
- この例はアクセス制御の学習用であり、整数の上限やマルチスレッド対応は扱っていない

**復習用演習**

### メモリ構造の基本

| 領域 | 学習上の主な役割 |
| --- | --- |
| メソッド領域 | クラスに関する情報などを管理 |
| JVMスタック | スレッドごとのメソッド呼び出しとフレームを管理 |
| ヒープ | インスタンスや配列を管理 |

- メソッド呼び出し時にフレームが作られ、終了すると取り除かれる
- ローカル変数には基本型の値やオブジェクトへの参照などが保持される
- ローカル変数の有効範囲が終わっても、他から参照されるオブジェクトは利用され続ける
- 到達不能になったオブジェクトはGCの回収対象になり得るが、直ちに回収される保証はない
- ここでの説明は概念モデルであり、JITの最適化や実際の物理的な配置まで一律に表すものではない

| データ構造 | 取り出し順序 | 例 |
| --- | --- | --- |
| スタック | LIFO：最後に入れたものが先 | メソッド呼び出しの復帰順序 |
| キュー | FIFO：先に入れたものが先 | 到着順の処理待ち |

### インスタンス変数とstatic変数

```java
class Counter {
    private static int total;
    private final String name;

    Counter(String name) {
        this.name = name;
        total++;
    }

    static int getTotal() {
        return total;
    }

    String getName() {
        return name;
    }
}
```

- `name`はインスタンスごとに保持する
- `total`はそのクラスで共有する状態を表す
- 厳密にはクラスローダーが異なれば、同名でも別のクラスとして扱われる場合がある
- `static`変数の実際の配置を、常に特定の物理メモリ領域と断定しない
- このカウンターの`total++`は、マルチスレッド環境での安全性を保証しない

### staticメソッドの注意点

- 特定のインスタンスなしで`Counter.getTotal()`のように呼び出せる
- `static`な文脈では`this`を使用できない
- インスタンスのフィールドやメソッドには、対象インスタンスの参照からアクセスする
- インスタンスメソッドからは、クラスの`static`メンバーを利用できる
- インスタンス経由でも呼び出せる場合があるが、所属を明確にするためクラス名を使用する
- 共有する可変状態を増やすと、変更の影響範囲やテストへの影響が広がりやすい

- インスタンスを二つ作り、個別の状態と共有状態を比較する

### 再代入を禁止する

```java
class Settings {
    static final int MAX_USERS = 100;
    private final String name;

    Settings(String name) {
        this.name = name;
    }
}
```

- `final`変数は、一度初期化すると別の値を代入できない
- 未初期化のインスタンスfinalフィールドは、各コンストラクタの正常終了までに初期化する必要がある
- `final`な引数にも別の値を再代入できない
- 共有する定数は`static final`で表すことが多く、名前は大文字とアンダースコアが慣例
- すべての`static final`がコンパイル時定数ではなく、型や初期化式の条件がある

### finalな参照と不変性の違い

```java
class Data {
    int value;
}

// メソッド内の例
// final Data data = new Data();
// data.value = 20;      // 参照先の変更は可能
// data = new Data();   // 再代入はコンパイルエラー
```

- `final`が固定するのは変数に保持する参照であり、参照先の全フィールドではない
- 配列の参照を`final`にしても、配列要素は変更できる
- 不変オブジェクトにするには、公開する操作や内部の可変データの扱いも設計する

**復習用演習**

- `final int[] values = {1, 2};`で要素変更と配列変数への再代入を比較する

### 共通機能の継承と拡張

```java
class Car {
    protected final String model;

    Car(String model) {
        this.model = model;
    }

    public void move() {
        System.out.println(model + "が移動する");
    }
}

class ElectricCar extends Car {
    ElectricCar(String model) {
        super(model);
    }

    @Override
    public void move() {
        super.move();
        System.out.println("電気モーターを使用する");
    }

    public void charge() {
        System.out.println("充電する");
    }
}
```

- `ElectricCar`は`Car`の一種である、というis-a関係を表す
- Javaのクラスは、直接の親クラスを一つだけ持つ
- 親の状態も子のインスタンスの一部であり、親と子が別々の二つのオブジェクトになるわけではない
- 親の`private`フィールドを子から直接操作することはできない
- コンストラクタは継承されず、親のコンストラクタを呼び出して初期化する
- 暗黙の`super()`が必要な場合、対応するアクセス可能な引数なしコンストラクタが親にないとコンパイルできない

### オーバーロードとオーバーライド

| 観点 | オーバーロード | オーバーライド |
| --- | --- | --- |
| 意味 | 同名で引数の異なるメソッドを定義 | 親のインスタンスメソッドを子で再定義 |
| 主な選択時点 | コンパイル時 | 実行時の対象インスタンスに応じて選択 |
| 注意点 | 戻り値だけの違いでは定義できない | アクセス範囲を狭められない |

- `@Override`を付けると、意図どおりの再定義かをコンパイラで確認できる
- 戻り値は同じ型、または許可された共変戻り値型にする
- チェック例外をより広くするなど、契約を破る変更はできない
- `static`メソッドは同じ意味でオーバーライドされず、隠蔽として扱われる
- コードの再利用だけを理由に継承せず、is-a関係が適切かを考える

**復習用演習**

- 共通の車の機能と、車種固有の機能を分ける
- `super.move()`を呼ぶ場合と、完全に処理を置き換える場合を比較する

### 参照型と実際のインスタンス

```java
class Parent {
    String value = "parent";
    void call() { System.out.println("Parent.call"); }
}

class Child extends Parent {
    String value = "child";
    @Override
    void call() { System.out.println("Child.call"); }
    void childOnly() { System.out.println("子の固有機能"); }
}

// メソッド内の例
// Parent target = new Child();
// target.call();                 // Child.call
// System.out.println(target.value); // parent
// target.childOnly();            // コンパイルエラー
```

- 親型の変数で子のインスタンスを参照できる
- 呼び出し可能なメンバーは、コンパイル時の参照型を基準に判断される
- オーバーライドされたインスタンスメソッドは、実行時のインスタンスに応じて選択される
- フィールドは同じように動的に選択されず、この例では参照型の`Parent`側が選ばれる

### アップキャストとダウンキャスト

```java
Child child = new Child();
Parent parent = child;              // アップキャスト
Child restored = (Child) parent;    // ダウンキャスト
restored.childOnly();

Parent plain = new Parent();
// Child invalid = (Child) plain;   // 実行時にClassCastException

if (parent instanceof Child) {
    Child checked = (Child) parent;
    checked.childOnly();
}
```

- アップキャストは通常、明示的なキャストを省略できる
- ダウンキャストは、実際のインスタンスが対象型として扱える場合だけ成功する
- キャストはオブジェクトを別の種類に作り変える操作ではない
- `null instanceof Child`は`false`になる
- `null`の参照をキャストしても`null`のままだが、その後のインスタンスメソッド呼び出しは例外になる
- `instanceof`による分岐が増える場合は、共通操作を多態性で表現できないか検討する

**復習用演習**

- 親型の変数に子を代入し、メソッドとフィールドの選択の違いを確認する

### 共通の型で処理する

```java
abstract class Animal {
    public abstract void sound();

    public void move() {
        System.out.println("移動する");
    }
}

class Dog extends Animal {
    @Override
    public void sound() { System.out.println("ワン"); }
}

class Cat extends Animal {
    @Override
    public void sound() { System.out.println("ニャー"); }
}

// メソッド内の例
// Animal[] animals = {new Dog(), new Cat()};
// for (Animal animal : animals) {
//     animal.sound();
// }
```

- 配列要素や引数を共通の型にすると、種類ごとの重複処理をまとめられる
- 抽象クラスは直接インスタンス化できない
- 抽象メソッドは本体を持たず、具象サブクラスが実装する必要がある
- 抽象クラスには、通常のメソッド、フィールド、コンストラクタも定義できる
- 抽象クラス自身に抽象メソッドが一つもない構成も可能

### インターフェースと複数実装

```java
interface Flyable {
    void fly();
}

interface Swimmable {
    void swim();
}

class Duck extends Animal implements Flyable, Swimmable {
    @Override
    public void sound() { System.out.println("ガー"); }
    @Override
    public void fly() { System.out.println("飛ぶ"); }
    @Override
    public void swim() { System.out.println("泳ぐ"); }
}
```

- 一つのクラスで複数のインターフェースを実装できる
- 基本形のインターフェースメソッドは`public abstract`であり、実装側も`public`にする
- インターフェースのフィールドは`public static final`として扱われる
- インターフェース型の変数を通して、役割に必要な操作だけを利用できる
- インターフェースには`default`、`static`、`private`メソッドを定義できるJavaのバージョンもあり、常にすべてのメソッドが抽象であるわけではない

| 比較 | 抽象クラス | インターフェース |
| --- | --- | --- |
| 主な目的 | 共通する状態・実装と抽象化 | 役割・契約の表現 |
| インスタンスフィールド | 定義可能 | 定義しない |
| コンストラクタ | 定義可能 | 定義できない |
| 複数の継承・実装 | クラスの直接の親は一つ | 複数実装可能 |

- `Flyable`を引数に受け取るメソッドから、飛行処理を呼び出す

### 役割と実装を分離する

- 役割は「何ができるか」を表し、実装は「どのように実現するか」を表す
- 利用する側が共通の役割に依存すると、具体的な実装を交換しやすくなる
- 多態性を利用するだけで、すべての変更箇所がなくなるわけではない
- インスタンスの生成・選択と、生成済みオブジェクトの利用を分けることが重要

**実行可能なコード例**

```java
interface Car {
    void start();
    void move();
}

class ElectricCar implements Car {
    @Override
    public void start() { System.out.println("電源を入れる"); }
    @Override
    public void move() { System.out.println("電気で走る"); }
}

class GasCar implements Car {
    @Override
    public void start() { System.out.println("エンジンを始動する"); }
    @Override
    public void move() { System.out.println("ガソリンで走る"); }
}

class Driver {
    private final Car car;

    Driver(Car car) {
        this.car = car;
    }

    void drive() {
        car.start();
        car.move();
    }
}

public class DesignMain {
    public static void main(String[] args) {
        Driver first = new Driver(new ElectricCar());
        Driver second = new Driver(new GasCar());
        first.drive();
        second.drive();
    }
}
```

- `Driver`は、`ElectricCar`や`GasCar`の個別の操作を知らなくてもよい
- 実装を選んで渡す責務は、この例では`main()`が持つ
- 外部から依存先を渡す方法は、依存性注入の基本形として理解できる
- 第9章の継承例とは別の例であり、同名の型を同じパッケージにまとめて配置しない

### OCP - 拡張に開き、修正に閉じる

| 変更 | 具象型ごとの分岐が利用側にある場合 | 共通の契約を利用する場合 |
| --- | --- | --- |
| 新しい車種を追加 | 利用側の分岐も追加しやすい | 新しい実装を追加する |
| 車種の選択 | 利用処理と混ざりやすい | 生成・組み立て側で選択する |
| 運転処理 | 具象型の詳細に依存しやすい | `Car`の契約に依存する |

- 新しい`Car`実装を追加しても、共通の契約が変わらなければ`Driver.drive()`を変更せずに利用できる
- 実装の追加に伴い、生成・組み立て側のコードを変更することはあり得る
- OCPは、あらゆる変更で既存コードを一切修正しないという意味ではない
- インターフェースのメソッド追加など、契約自体の変更は既存実装へ影響する
- 名前だけ同じでも、契約に反する実装では安全に交換できない
- 想定する変更に対して、どの部分を安定させるかを考える
