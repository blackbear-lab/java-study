## 1. ジェネリクス - Generic1

### ジェネリクスが必要な理由
- 型ごとに同じ機能を持つクラスを作成すると、コードが重複する問題が発生する
- 型が異なるだけで処理内容が同じ場合、共通の仕組みを利用してコードを再利用することが望ましい
- Javaでは、型に依存しない汎用的なコードを作成するためにジェネリクスを使用する

### 多態性による重複解消
- `Object`型を使用すると、さまざまな型のオブジェクトを同じクラスで扱うことができる
- 型ごとにクラスを定義する必要がなくなり、コードの重複を減らすことができる
- ただし、`Object`型で取得した値を元の型として使用するにはダウンキャストが必要になる
- 誤った型にダウンキャストすると、実行時に`ClassCastException`が発生する可能性がある

### ジェネリクス
- クラスやインターフェース、メソッドなどで型をパラメータとして扱う仕組み
- 型をあらかじめ固定せず、使用する側で具体的な型を指定できる
- 1つのクラスを異なる型で再利用できる
- 型安全性を確保しながら、コードの重複を減らすことができる

### ジェネリッククラス
- 型パラメータを持つクラスをジェネリッククラスという
- `class GenericBox<T>`のように、クラス名の後ろに型パラメータを定義する
- `T`は具体的な型が指定されるまで仮の型として使用される
- クラス内部では、フィールドやメソッドの型として`T`を使用できる

### 型パラメータと型引数
- 型パラメータは、ジェネリッククラスなどを定義する際に使用する仮の型
- `T`、`E`、`K`、`V`などが一般的に使用される
- 型引数は、ジェネリッククラスを使用する際に指定する具体的な型
- `GenericBox<String>`の場合、`T`が型パラメータ、`String`が型引数になる
- 型引数には基本型を直接指定できないため、`Integer`などの参照型を使用する

### ジェネリクスの型安全性
- ジェネリクスを使用すると、コンパイル時に型の不一致を検出できる
- 指定した型と異なる値を渡そうとするとコンパイルエラーになる
- `Object`型を使用する場合と異なり、値を取得するときに明示的なダウンキャストが不要になる
- 実行時の型変換エラーを防ぎやすくなる

### ジェネリクスの活用
- 同じ処理を異なる型のデータに対して再利用できる
- 型ごとに同じクラスを作成する必要がなくなる
- 型引数を変更することで、同じジェネリッククラスをさまざまな型で使用できる
- コードの再利用性、可読性、保守性を高めることができる

### ジェネリクスを使用するメリット
- 型ごとのコードの重複を削減できる
- コンパイル時に型の不一致を検出できる
- 不要なダウンキャストを減らすことができる
- 1つのクラスをさまざまな型で再利用できる
- 型安全性とコードの保守性を向上させることができる

## 2. ジェネリクス - Generic2

### 型パラメータの制限
- 型パラメータに制限を指定しない場合、`Object`型で定義されているメソッドしか直接使用できない
- 特定のクラスを継承した型だけを扱いたい場合は、型パラメータに上限境界を指定する
- `<T extends クラス名>`のように定義することで、指定したクラスとそのサブクラスのみを型引数として使用できる
- 型パラメータに制限を設けることで、指定したクラスのメソッドを安全に呼び出せる

### 多態性と型パラメータの制限
- 多態性を利用すると、親クラスの型で子クラスのオブジェクトを扱うことができる
- ただし、親クラスの型で値を返す場合、子クラス固有の機能を利用するにはダウンキャストが必要になることがある
- ジェネリクスを利用すると、型引数として指定した具体的な型を維持できる
- `<T extends 親クラス>`を使用することで、多態性と型安全性を組み合わせることができる

### ジェネリックメソッド
- メソッド単位で型パラメータを定義する仕組み
- `public static <T> T method(T value)`のように、戻り値の型の前に型パラメータを宣言する
- ジェネリッククラスとは異なり、クラス全体ではなく特定のメソッドだけで型パラメータを使用する
- 通常のクラスにもジェネリックメソッドを定義できる
- メソッドごとに異なる型引数を指定できる

### ジェネリックメソッドの活用
- ジェネリックメソッドでは、型引数を明示的に指定して呼び出すことができる
- Javaの型推論により、引数などから型を判断できる場合は型引数を省略できる
- ジェネリックメソッドにも`<T extends クラス名>`による型パラメータの制限を指定できる
- 型パラメータを利用することで、引数と戻り値の型の関係を維持できる
- 同じ処理をさまざまな型に対して再利用できる

### ワイルドカード
- ワイルドカードは、ジェネリクスの型引数に`?`を使用する仕組み
- `<?>`は、具体的な型引数を特定しない場合に使用する
- 異なる型引数を持つジェネリッククラスを、共通のメソッドで扱うことができる
- ワイルドカードは型パラメータを新しく定義するものではない
- 引数と戻り値の型を関連付ける必要がない場合などに活用できる

### 上限境界ワイルドカード
- `<? extends T>`は、指定した型またはそのサブタイプを受け入れる
- 特定の親クラスを継承した型や、インターフェースを実装した型を扱う場合に使用する
- 型の範囲を制限しながら、共通の処理を実装できる
- 上限境界を指定することで、指定した型のメソッドを安全に利用できる
- 具体的な型引数が不明なため、原則として`null`以外の値を追加することはできない

### 下限境界ワイルドカード
- `<? super T>`は、指定した型またはそのスーパータイプを受け入れる
- 特定の型の値を追加する処理などに利用できる
- `T`型のオブジェクトやそのサブタイプのオブジェクトを安全に追加できる
- 取得した値は、基本的に`Object`型として扱う必要がある
- 上限境界ワイルドカードとは、型の制限方向と利用目的が異なる

### ジェネリックメソッドとワイルドカードの違い
- ジェネリックメソッドは、型パラメータを宣言してメソッド内で使用する
- ワイルドカードは、型パラメータを宣言せずにさまざまな型引数を受け入れる
- 引数と戻り値などの型を関連付けたい場合は、ジェネリックメソッドが適している
- 型の関係を維持する必要がない場合は、ワイルドカードを使用すると簡潔に記述できる
- 用途に応じて使い分けることで、柔軟で型安全なコードを作成できる

### 型イレイジャー（型消去）
- Javaのジェネリクスは、主にコンパイル時に型安全性を確認する仕組み
- コンパイル時に型パラメータの情報が消去され、適切な型に置き換えられる
- 型パラメータに制限がない場合は、基本的に`Object`型に置き換えられる
- `<T extends クラス名>`のように上限境界が指定されている場合は、その上限の型に置き換えられる
- 型消去によって、実行時にはジェネリクスの具体的な型引数を区別できない場合がある
- 型パラメータを使用して`new T()`のように直接インスタンスを生成することはできない

### ジェネリクスのまとめ
- 型パラメータの制限を利用すると、特定の継承関係にある型だけを扱うことができる
- ジェネリックメソッドを利用すると、メソッド単位で汎用的な処理を実装できる
- ワイルドカードを利用すると、異なる型引数を持つジェネリッククラスを柔軟に扱える
- `extends`と`super`は、扱う型の範囲と用途に応じて使い分ける
- 型イレイジャーの仕組みを理解することで、ジェネリクスの制約を把握できる
- ジェネリクスを適切に活用することで、型安全性、再利用性、保守性を高めることができる

## 3. コレクションフレームワーク - ArrayList

### 配列の基本構造とインデックス
- 配列は、同じ型の複数の要素をインデックスで管理するデータ構造
- インデックスは`0`から始まり、配列の長さが`n`の場合、最後のインデックスは`n - 1`になる
- インデックスを指定すると、目的の要素に直接アクセスできる
- 配列の長さは生成時に決まり、生成後に変更することはできない
- 範囲外のインデックスにアクセスすると、`ArrayIndexOutOfBoundsException`が発生する

### ビッグオー記法（O記法）
- データ数の増加に対して、処理量がどの程度増えるかを表す記法
- 実際の実行時間ではなく、処理量の増加傾向を表す
- `O(1)`は、データ数にかかわらず処理量がほぼ一定であることを示す
- `O(n)`は、データ数に比例して処理量が増えることを示す
- 定数倍や影響の小さい項を省略し、増加傾向に注目する
- 同じデータ構造でも、取得・検索・追加・削除によって時間計算量が異なる

### 配列の取得と検索
- インデックスを指定した要素の取得は、直接アクセスできるため`O(1)`になる
- 値を指定して要素を検索する場合は、先頭から順番に比較する必要がある
- 目的の要素が末尾にある場合や存在しない場合は、すべての要素を確認する
- このような線形探索の時間計算量は、最悪の場合`O(n)`になる

### 配列へのデータ追加
- 配列を使って要素を管理する場合、追加位置によって必要な処理が異なる
- 空き容量がある場合、末尾への追加は要素の移動が不要なため`O(1)`になる
- 先頭や中間への追加では、追加位置以降の要素を後ろにずらす必要がある
- 先頭への追加は、既存のすべての要素を移動するため`O(n)`になる
- 中間への追加も、最悪の場合`O(n)`になる
- 空き容量がない場合は、より大きい配列を用意する必要がある

### 独自の配列リスト
- 配列を内部に持ち、要素の追加や取得などを提供するクラスを実装する
- 配列そのものの長さと、実際に格納されている要素数を分けて管理する
- `size`は、実際に格納されている要素数を表す
- 容量（capacity）は、内部配列に格納できる要素数の上限を表す
- 空き容量がある場合、`size`と容量は一致しない
- リストの要素を扱う際は、内部配列の長さではなく`size`を基準にする

### 動的配列と容量の拡張
- 動的配列は、必要に応じて内部配列を置き換え、容量を拡張する仕組み
- 配列自体の長さを変更するのではなく、より大きい配列を新しく生成する
- 新しい配列に既存の要素をコピーし、内部配列の参照を更新する
- `Arrays.copyOf()`などを利用すると、要素をコピーした新しい配列を生成できる
- 容量の拡張時には既存の要素をコピーするため、`O(n)`の処理が発生する
- 容量を一定の倍率で拡張する場合、末尾への追加は償却時間計算量で`O(1)`になる

### 要素の取得・変更・検索
- `get(index)`は、指定した位置の要素を取得する
- `set(index, value)`は、指定した位置の要素を別の値に変更する
- インデックスによる取得と変更は、要素の移動が不要なため`O(1)`になる
- `indexOf(value)`は、指定した値と一致する要素の位置を検索する
- オブジェクトの内容を比較する場合は、参照の比較ではなく`equals()`を使用する
- 検索対象に`null`を許可する場合は、比較時の`NullPointerException`に注意する
- 線形探索による検索は、最悪の場合`O(n)`になる

### 指定位置への追加
- 指定した位置に要素を追加する場合、追加位置以降の要素を1つずつ後ろに移動する
- 既存の要素を上書きしないように、末尾側から順番に移動する
- 要素を移動した後、空いた位置に新しい値を格納する
- 追加後は`size`を1増やす
- 追加前に空き容量を確認し、必要に応じて内部配列を拡張する
- 先頭や中間への追加は、最悪の場合`O(n)`になる

### 指定位置の削除
- 指定した位置の要素を削除した後、後続の要素を1つずつ前に移動する
- 後続の要素は、削除位置の次から順番に移動する
- 削除後は`size`を1減らす
- 使用しなくなった末尾の位置には`null`を代入する
- 不要な参照を残さないことで、ほかから参照されていないオブジェクトがGCの回収対象になれる
- 末尾の削除は`O(1)`、先頭や中間の削除は最悪の場合`O(n)`になる

### インデックスの範囲
- 取得・変更・削除で指定できる範囲は、`0`以上`size`未満になる
- 追加では末尾の次にも挿入できるため、`0`以上`size`以下を指定できる
- 内部配列の容量内であっても、リストの有効範囲内とは限らない
- 不正なインデックスを受け取った場合は、例外を発生させて処理を中断する

### 配列リストへのジェネリクスの適用
- `Object`型だけで実装すると、異なる型の値が混在する可能性がある
- 値を取得するときに、利用側でダウンキャストが必要になる
- `class MyArrayList<E>`のように型パラメータを定義すると、扱う要素の型を指定できる
- 追加・取得・変更などのメソッドに`E`を使用することで、型の関係を維持できる
- 指定した型と異なる値の追加を、コンパイル時に検出できる
- 利用側では、明示的なダウンキャストをせずに値を取得できる

### ジェネリクスと内部配列
- 型消去の制約により、`new E[容量]`のように型パラメータの配列を直接生成できない
- 内部配列に`Object[]`を使用し、取得時に`E`へキャストする方法などがある
- 内部でキャストする場合でも、公開するメソッドを通して要素の型を制御することが重要
- 未チェックキャストの警告を抑制する場合は、安全性を確認したうえで必要な範囲に限定する
- 内部の実装と、利用側に提供する型安全な操作を分けて考える

### ArrayListの時間計算量

| 操作 | 時間計算量 | 理由 |
| --- | --- | --- |
| インデックスによる取得 | O(1) | 指定位置に直接アクセスできる |
| インデックスによる変更 | O(1) | 指定位置の値を置き換える |
| 値による検索 | O(n) | 要素を順番に比較する |
| 末尾への追加 | 償却O(1) | 通常は直接追加できるが、容量拡張時はO(n)になる |
| 先頭・中間への追加 | O(n) | 後続の要素を移動する |
| 末尾の削除 | O(1) | 後続の要素を移動する必要がない |
| 先頭・中間の削除 | O(n) | 後続の要素を前に移動する |

### ArrayListのまとめ
- ArrayListは、配列を内部に持つリスト構造
- 要素数と内部配列の容量を分けて管理する
- 必要に応じて容量を拡張できるため、要素数の増加に対応できる
- インデックスによる取得・変更や、末尾への追加に適している
- 先頭や中間への追加・削除では、要素の移動による負荷が発生する
- ジェネリクスを組み合わせることで、型安全なリストを実装できる
- データ構造を選ぶ際は、頻繁に行う操作と時間計算量を考慮する
